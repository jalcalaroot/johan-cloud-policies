# Azure plan_only fixtures

`good.json` / `bad.json` are hand-crafted Terraform plan JSON, not
generated by a real `terraform plan`. Unlike AWS, the `azurerm` provider
requires real authentication even to plan a brand-new resource with no
data source lookups — confirmed by hand: a plan using placeholder
`client_id`/`client_secret`/`tenant_id` fails immediately with
`AADSTS700038: ... is not a valid application identifier`, before
Terraform ever gets to the resource itself. There's no AWS-style
`skip_credentials_validation` escape hatch for this provider.

Both files follow the exact schema `terraform show -json` produces
(`format_version`, `planned_values.root_module.resources[].values`,
`resource_changes[].change.after`) — verified against a real plan
generated for the equivalent AWS case in `test/plan_only/aws/`, then
hand-adapted for `azurerm_role_assignment` with already-resolved `scope`
values (a real plan would never leave `scope` as the raw
`azurerm_management_group.x.id`-style reference — Terraform inlines the
actual ARM resource ID before this JSON is produced).

This checked-in JSON gets replaced by a real one automatically once this
check runs for real in a consuming repo's `gha-checkov-plan-scan` step —
this fixture only needs to prove the check's *logic* is correct against
the resolved shape, not reproduce Azure auth locally.
